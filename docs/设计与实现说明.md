# 设计与实现说明

## 1. 这一版要解决什么问题

这次工作的目标是：先建立能运行、能跳转、接近效果图、方便在 VS Code 继续开发的前端项目。用户允许界面数据写死，但要求保留接口和返回值。因此，本版优先完成可复用的页面框架和可替换的数据入口。

两份补充文档与七份开发规范描述的是最终完整平台，其中包括真实任务、数据库、日志、版本和测试留痕。本版只完成其中的前端阶段，不把模拟执行描述为真实算法结果，也不声称已经满足完整平台的验收要求。

以下内容记录设计依据、实现取舍和后续路线，便于其他开发人员理解代码。

## 2. 为什么选 Vue 3 这套技术栈

开发规范已明确 Vue 3、TypeScript、Vite、Pinia、Element Plus、ECharts，因此遵循原有选型，减少后续多人协作和联调时的技术差异。

| 技术         | 在本项目中的作用               | 选择依据                                     |
| ------------ | ------------------------------ | -------------------------------------------- |
| Vue 3        | 组件与页面展示                 | 各页面有大量重复面板，适合组件化组织         |
| TypeScript   | 参数和响应类型约束             | 对接口字段提前校验，减少联调时才发现拼写错误 |
| Vite         | 开发服务和构建                 | 支持 Vue 单文件组件与快速调试                |
| Vue Router   | 一级导航与二级 Tab             | 页面可以直接打开、刷新和通过浏览器前进后退   |
| Pinia        | 任务与资源数据管理             | 多个页面和任务抽屉共享同一份状态             |
| Element Plus | 表格、表单、弹窗和提示         | 复用交互控件，集中精力实现业务页面           |
| ECharts      | 折线、雷达、环形、柱形和热力图 | 支持参考图中的主要统计形式                   |

没有将截图铺成背景。标题、导航、表格和图表均为真实前端元素，才能继续添加业务交互和后端数据。

## 3. 为什么菜单按平台能力组织

补充映射文档明确：课题编号用于后台研发责任划分，前端展示项目整体能力。因此菜单显示“数据治理”“模型训推”“全链路合规治理”等名称，不显示“课题一”“课题二”。

规范原来是八个一级菜单，但用户明确列出了九个，并同时提到“模型训练”和“模型训推”。本版保留九个入口：模型训练是独立工作入口，模型训推覆盖训练、管理、评估、部署和调用。

这两个模块暂时复用 `ModelPage.vue`，减少相同统计卡、训练概况和模型列表的重复代码。后续业务变复杂后，可以拆为独立训练工作台，不影响现有路径。

二级功能使用真实 URL，而不是仅改变按钮颜色。部分二级路由目前共享模块总览，这是框架阶段的取舍：路由、标题与业务入口先就绪，独立业务详情逐步扩展。

## 4. 为什么分成布局、组件、页面和接口层

```text
布局 AppLayout
  ├─ 顶部品牌、搜索、任务、消息、用户
  ├─ 左侧一级菜单
  └─ 主区路由页面
       ├─ 指标卡 / 内容面板 / 图表 / 表格
       └─ Pinia 状态
            └─ API 函数
                 ├─ Mock 返回值
                 └─ 真实 HTTP 请求
```

布局负责所有页面共有的部分，避免九个页面各写一份导航。页面负责组合业务模块；表格、图表和面板通过组件复用。请求通过 API 层处理，不散落在按钮事件中。

这样修改品牌名、侧栏宽度或颜色时只需改一处；替换接口时，也不需要逐个寻找页面中的请求地址。

当前资源表格是通用展示组件，适合快速搭框架；正式接入时，数据集、模型、指标的字段不同，应分别建立完整 DTO 与领域表格，避免通用组件承载过多业务条件。

## 5. 为什么预留接口采用 Promise 和显式 return

即使现在使用固定数据，也让调用方式接近真实请求：

```ts
export async function executeTask(data: ExecuteTaskReq): Promise<Task> {
  if (isMock) {
    return mockTask
  }
  return request({ url: '/tasks/execute', method: 'POST', data })
}
```

上例是结构说明，完整可运行实现位于 `src/api/task.ts`。

这样页面始终通过 `await` 获取结果，可以共用加载、成功和失败状态。后端接入后主要替换数据来源，而不是把同步写死的页面重新改成异步页面。

`return` 不只是占位：当前模拟分支确实返回任务 ID、状态、时间、耗时和结果，真实分支确实返回解包后的后端响应。为避免误导，模拟任务使用 `mock_` 前缀并标注示例数据。

## 6. 为什么用统一能力入口

两份补充文档把四个课题划分为数据价值、数据异常、语义风险、全链路审计。前端不应该知道算法部署在哪台服务器，也不应该直接调用课题适配器。

因此统一调用 `POST /api/v1/tasks/execute`，通过 `capability_code` 告诉平台要执行哪项能力。能力登记在 `src/api/capability.ts`，共 20 项。

采用 `/api/v1` 是因为正式 API 规范明确要求路径版本号；补充思路文档中 `/api/tasks/execute` 视为概念性示意。

算法从固定数据换成大模型，或从大模型换成课题真实算法时，原则上由后端适配器处理，前端继续使用同一能力编码和契约。

## 7. 为什么集中转换字段与错误

规范要求后端 JSON 使用 snake_case，前端使用 camelCase。请求层集中转换对象和数组中的字段名，但不改变 `semantic_risk`、`high` 这类字段值。

例如页面传 `datasetId`，网络发送 `dataset_id`；后端返回 `trace_id`，前端读取 `traceId`。统一响应体在请求层解包，业务错误和网络错误统一提示。

鉴权 token 仅在存在时携带；Trace ID 由真实后端生成后回传，Request ID 用于标识请求。本版未实现登录与权限控制，不能把演示管理员界面当作权限安全边界。

## 8. 为什么采用现在的视觉结构

五张效果图共同具有深蓝顶栏与侧栏、浅蓝背景、白色圆角面板、亮蓝选中状态、多列 KPI 和密集业务概览。本版沿用这一视觉结构，保持平台的一致性。

首页先显示总体指标，再显示核心任务链，随后是场景入口、最近任务和支撑能力。这种顺序回答“总体情况如何、治理流程是什么、下一步从哪里进入”。

数据治理突出价值分析、异常比例和风险列表；模型页面突出训练过程、调用表单和模型管理；合规页面突出链路节点、推理步骤与热力图；测试页面突出指标、执行与结果。

图表使用 ECharts 绘制，容器尺寸变化时自动调整，离开页面时释放实例。装饰性背景采用 CSS，避免依赖截图里的文字和不可编辑素材。当前为视觉风格复现，并非像素级还原。

## 9. 为什么不把真实功能做成假成功

模拟任务完成时明确显示“模拟调用完成”；页面右上角标注“原型演示 · 示例数据”。真实上传、模型部署、角色权限修改等尚未接后端的动作，不宣称已执行。

原因是补充实施思路强调“平台机制真实，课题算法可模拟”。这一版经用户授权只做前端；进入完整平台阶段后，必须把任务、结果、日志、版本等交给真实后端保存。

切换 `VITE_USE_MOCK=false` 只会让已封装的接口走网络，不代表所有 KPI、图表、通知和权限自动变成真实功能。这些仍需分模块对接。

## 10. 如何验证这份代码

- TypeScript 检查：验证组件参数和代码类型。
- ESLint 与 Prettier：检查代码质量与格式。
- 生产构建：验证页面组件能够编译输出。
- 接口契约测试：验证递归字段转换、枚举值保留、20 个能力入口与路由匹配。
- 浏览器检查：访问一级和二级路由，验证模拟调用、任务抽屉、消息和搜索，并检查移动端横向溢出。
- 页面截图：检查实际显示效果，不能仅凭构建成功判断页面可用。

验证过程曾发现模板内多条点击语句被格式化后导致编译错误，已改为具名事件处理函数。这个修正也使事件逻辑更容易阅读和维护。实际验收结果见同目录验证文件。

## 11. 下一步建议的开发顺序

1. 固定任务、数据集、模型、指标和日志的真实 API 契约，为领域资源补齐类型定义。
2. 建立真实任务创建与执行、结果保存、日志、版本 ID 和状态流转。
3. 接通数据资源列表与上传，再打通一个“数据 → 治理 → 模型 → 审计 → 结果”的完整链路。
4. 补齐测试指标的中期和完成期阈值，以及输入、时间、接口、版本、输出五项留痕。
5. 将各页面静态 KPI、图表与通知替换为真实统计接口。
6. 逐步替换算法适配器，并加入登录、权限校验、真实训练和部署服务。

优先跑通完整业务链，比同时把所有图表做成复杂动画更有助于验证平台设计。
