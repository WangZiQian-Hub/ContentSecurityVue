# 场景应用 · 模型服务对接说明

对接对象：模型服务（《前端直连 API 文档》描述的服务，地址 `http://127.0.0.1:8001`）
前端仓库：`content-safety-platform`
涉及页面：场景应用 —— 舆情分析 / 热点事件跟踪 / 跨文化交流 / 多民族社会治理 / 智能政务 / 网络空间安防

## 一、现状：8001 上跑的不是模型服务

前端六个页签已按《前端直连 API 文档》开发完成，`/llm-api` 代理也已配通。

**但当前 8001 端口上运行的是内容安全治理业务后端的第二个实例**，与 8000 完全相同：

| 检查项 | 8000 | 8001 |
| --- | --- | --- |
| 接口标题 | 内容安全治理平台 | 内容安全治理平台 |
| 路径总数 | 88 | 88 |
| 路径列表 | 完全一致 | 完全一致 |

文档中描述的接口在 8001 上**全部不存在**：

```
/api/v1/analysis/options            不存在
/api/v1/analysis/scenarios          不存在
/api/v1/analysis/model-governance   不存在
/api/v1/analysis/audits             不存在
/api/v1/analysis/records            不存在
/api/v1/llm/response-types          不存在
/api/v1/llm/invoke                  不存在
/api/v1/calls                       不存在
/api/v1/training/tasks              不存在
```

注意：模型服务**必须校验令牌**。文档第 9–16 行写明所有接口都携带
`Authorization: Bearer <本项目签发的访问令牌>`；而 8001 上的 `/api/v1/data-governance/options`
不带令牌就返回 200 —— 这本身就说明它不是模型服务。

**需要做的：把模型服务起在 8001。**

## 三、前端调用的 4 个接口

所有请求经网站代理地址 `/llm-api/v1` 发出，代理规则为 `/llm-api` → `/api`，
即 `/llm-api/v1/models` 实际访问 `http://127.0.0.1:8001/api/v1/models`。

### 3.1 `GET /api/v1/models` —— 填充模型下拉框

请求：无查询参数，带 Bearer 令牌。

响应 `data` 必须是**裸数组**：

```json
[
  {
    "model_id": "model-example",
    "upstream_model_id": "provider-model-name",
    "name": "内容分析模型",
    "description": "示例配置",
    "base_url": "https://provider.example/v1",
    "created_at": "2026-10-09T00:00:00+00:00",
    "updated_at": "2026-10-09T00:00:00+00:00"
  }
]
```

- ⚠️ **不是** `{"items": [...]}`。前端对返回结构做了严格校验，拿到分页对象会直接报错。
  原因是业务后端的模型条目使用数字 `id`，若被当作 `model_id` 发送出去只会得到 404。
- `description` 允许为 `null`。
- 空目录返回 `[]`，页面会提示「模型服务尚未配置可用模型」。
- 不需要提供 `api_key`。

### 3.2 `POST /api/v1/analysis/scenarios` —— 点「开始场景分析」

前端**按场景条件拼装请求体，不会发送额外字段**（文档第 105 行要求该请求不接受其他字段）：

```json
{
  "model_id": "model-example",
  "scenario_code": "hot_events",
  "content": "待分析的正文",
  "language": "zh",
  "materials": [
    { "id": "m1", "title": "预警通报", "time": "2026-07-01", "content": "发布暴雨橙色预警……" }
  ],
  "target_language": "en"
}
```

发送规则：

- `materials` **仅在用户填写了参考材料时**发送，最多 50 条。
- `target_language` **仅在 `cross_cultural` 场景**发送。
- `language` 仅在跨文化交流由用户选择，其余五个场景固定发送 `zh`。
- 用户侧已做校验：正文不超过 50000 字符、正文与材料合计不超过 200000 字符、
  材料 ID 唯一且不能为保留值 `input`、`id`/`title`/`time` 不超过 128 字符、
  语言字段必须为语言代码（如 `zh`、`en`、`zh-CN`）而非语言名称。

响应：`data` 为文档第 7 节的 AnalysisRecord，`data.result` 为文档第 4.2 / 4.3 节的场景结果。

**前端超时设置为 180 秒**（文档第 553 行给出上游单次超时 120 秒，留出余量）。

**失败时请按文档第 7.3 节处理**：返回非 2xx，但 `data` 中仍须带回那条记录
（含 `id`、`status`、`stage`、`error_code`、`original_output`）。
前端依靠它向用户说明「失败在哪一阶段、记录已保存」，而不是只弹一条错误。
若 `data` 为 `null`（鉴权失败、请求校验失败、模型不存在、并发满额尚未执行），
前端会按普通错误处理。

### 3.3 `GET /api/v1/analysis/records` —— 底部「场景分析记录」表

查询参数：

| 参数 | 值 |
| --- | --- |
| `kind` | `scenario` |
| `scenario_code` | 当前页签对应的场景编码 |
| `page` | 从 1 开始 |
| `page_size` | `10` |

响应 `data`：`{ items, total, page, page_size, total_pages }`

- 文档第 298 行说明该接口**不支持** `model_id` / `service_id` / `version` 筛选，前端未传。
- 前端按 `status` 区分三种状态：`succeeded`（已完成）、`failed`（失败）、`running`（进行中）。
  **`running` 不能当成失败显示** —— 文档第 325 行说明进程异常终止可能遗留 `running`。

### 3.4 `GET /api/v1/analysis/records/{id}` —— 点「查看」查看历史记录

响应 `data` 为单条 AnalysisRecord。前端会从 `data.input` 中取出 `content` 与 `materials`
显示在「① 输入原文」，因此**保存的请求快照必须完整保留正文与材料**。

## 四、前端渲染依赖的字段

以下字段缺失会导致页面对应区块空白，请确保返回。

### 4.1 共同字段（文档第 4.2 节）

| 字段 | 前端用途 |
| --- | --- |
| `summary` | 「结论速览」的主文案 |
| `risk_level` | 风险徽章，取 `low` / `medium` / `high` / `unknown` |
| `evidence` | 「引用来源」列表 |
| `recommendations` | 「建议」列表 |
| `limitations` | 「分析局限」列表 |
| `insufficient_materials` | 为 `true` 时显示「资料不足，结论不可用」提示 |
| `details` | 场景专属内容，见下表 |

### 4.2 各场景 `details` 字段（文档第 4.3 节）

| `scenario_code` | `details` 字段 |
| --- | --- |
| `public_opinion` | `sentiment`、`sentiment_evidence`、`issues`、`controversies`、`communication_advice` |
| `hot_events` | `event_summary`、`timeline`、`focal_points`、`contradictions`、`information_gaps`、`trend` |
| `cross_cultural` | `cultural_contexts`、`ambiguities`、`expression_suggestions`、`translation` |
| `ethnic_governance` | `issues`、`misunderstandings`、`conflict_expressions`、`coordination_advice` |
| `smart_government` | `answer`、`policy_claims`、`processing_points` |
| `cyber_security` | `risk_types`、`suspicious_signs`、`handling_advice` |

### 4.3 前端已处理的可空字段

| 字段 | 为 `null` / 空时的表现 |
| --- | --- |
| `trend` | 显示「材料不足，无法判断趋势。」 |
| `translation` | 整个「参考译文」区块不显示 |
| `policy_claims`、`processing_points` | 显示「无」 |
| `evidence`、`issues` 等数组 | 显示「无」 |

另：`Claim[]` 是**对象数组**（`{text, evidence:[{source_id, quote}]}`），不是字符串数组，
前端已按对象渲染。

## 五、待确认的两个问题

### 5.1 场景结果能否返回模型原始回答

目前场景结果只有结构化字段（`summary` + `details`），用户看不到模型原本如何组织语言。

热点场景最能说明问题：用户输入「希望梳理事件脉络与信息缺口」，返回的字段里
虽然有「事件时间轴」和「信息缺口」，但**没有一段连贯的叙述**。

**建议二选一：**

- **方案 A（推荐）**：把记录里的 `original_output` 对场景类型也填上
  （文档第 281 行目前说明该字段只用于生成治理，其他类型为 `null`）
- **方案 B**：在 `result` 中新增 `raw_output: string`

前端位置已经留好（「③ 输出结果 → 模型完整回答」），**有值就显示，无值整块不出现**，
不需要前端再改代码。

### 5.2 `recommendations` 与场景专属建议的分工

文档对 `recommendations` 的全部说明只有「建议，不表示已执行」，未说明：

1. 它和场景专属建议（`communication_advice`、`expression_suggestions`、
   `coordination_advice`、`handling_advice`）**分工是什么？会重复吗？**
2. 它面向谁？是给操作人员的处置建议，还是别的？
3. **热点和政务没有专属建议字段，是设计如此还是遗漏？**

前端目前把 `recommendations` 单独显示为「建议」，场景专属建议显示在场景区块内，
两者并存。确认后可决定是否合并。

## 七、常见现象对照

| 页面现象 | 原因 |
| --- | --- |
| 「模型目录返回的不是模型数组，当前地址可能不是模型服务」 | `GET /models` 返回了 `{items:[...]}`，说明 8001 上不是模型服务 |
| 「接口返回 404：当前地址上可能不是模型服务，或 /analysis/records 尚未实现」 | `GET /analysis/records` 未实现 |
| 点「开始场景分析」弹出 404 | `POST /analysis/scenarios` 未实现 |
| 「尚未填写模型服务访问令牌」 | 令牌栏未填写 |
| 「模型服务访问令牌无效或已失效」 | 令牌过期或被停用 |
| 页面顶部显示「当前为演示数据」 | 演示开关 `VITE_SCENARIO_DEMO=true` 仍开着 |
| 「模型服务尚未配置可用模型，请联系模型接入同学」 | `GET /models` 返回空数组 |
| 记录表出现「进行中」 | 记录状态为 `running`，非失败 |

## 八、附：令牌与数据隔离

- 令牌由模型服务签发，业务登录令牌与上游模型 API Key 均不能替代（文档第 16 行）。
- 记录、结果与任务查询**按令牌隔离**，跨令牌查询返回 404（文档第 31 行）。
  因此**更换令牌后，此前产生的历史记录在前端将不可见**，这属于预期行为。
- 前端将令牌保存在 `sessionStorage`：刷新页面仍有效，关闭标签页后需重新填写。
