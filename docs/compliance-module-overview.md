# 全链路合规治理 · 模块说明

> **用途**：汇报 / 交接用。讲清楚这个模块有哪几个页面、每个页面解决什么问题、数据从哪来、判定口径是什么。
> **面向对象**：不需要懂代码也能看懂；技术细节放在每个页面最后的「数据来源」小节。
> **配套文档**：给后端的对接需求见 [compliance-backend-requirements.md](./compliance-backend-requirements.md)。

---

## 一、这个模块要解决什么问题

平台里的数据、任务、模型分散在各自的模块：数据资源、数据治理、模型训推、场景应用。
**每件事单独看都没问题，但串起来看就可能出现「接不上」的情况：**

| 典型问题 | 例子 |
|---|---|
| **链路断了** | 训练用了一份数据，但那份数据在资源库里根本没登记 |
| **任务缺项** | 一条治理任务跑了，但该留的原始字段（五要素）没留全 |
| **模型隐患** | 训练任务说要存 4 个检查点，实际只存了 1 个 |

**「全链路合规治理」就是把这三类问题集中查出来、说清楚、能追到证据。**

## 三、页面的共同逻辑：三层检查

**这是整个模块的灵魂。** 所有页面查的都是这三层，只是深度不同。

| 层级 | 检查什么 | 通俗解释 | 怎么判定 |
|---|---|---|---|
| **链路层** | 4 类交接关系 | **前后两件事接上了没有** | 谱系图上的边，`verification_state` 不是 `verified` 就是断的 |
| **任务层** | 任务执行状态 | **这件事跑成功了没有** | `status === 'failed'` |
| **模型层** | 检查点齐全 + 神经元激活 | **模型内部正常吗** | 应有检查点数 − 实际保存数；神经元激活超阈值单元数 |

### 链路层的 4 类交接关系

```
数据版本 ──①输入数据引用──▶ 治理任务 ──②治理版本登记──▶ 训练数据版本
                                                              │
                                                             ③训练数据绑定
                                                              ▼
                                                          训练任务
                                                              │
                                                             ④训练产物登记
                                                              ▼
                                                          模型版本
                                                              │
                                                             ⑤模型版本引用
                                                              ▼
                                                          推理调用
```

> **"关系表示工程依赖，不表示因果关系"** —— 这句话在页面上也写着，
> 因为这是**证据链**，不是**因果推断**。

### ③ 全链路追踪 `/compliance/full-chain`

**干什么**：**看"该留的字段留全了没有"** —— 选一条任务，检查它的**五要素证据**。

#### 什么是"五要素"

一条任务执行完，应该留下 **5 个关键字段**的原始记录：

| # | 要素 | 通俗解释 | 例子 |
|---|---|---|---|
| 1 | **输入** `input` | 喂进去的是什么 | `v1.0.0` |
| 2 | **时间** `time` | 什么时候跑的 | `2026-10-05T19:55:17` |
| 3 | **接口** `interface` | 用的什么处理流程 | `标准清洗流程 → normalize_text → 去重与补全 → complete_fields` |
| 4 | **版本** `version` | 用的哪个版本 | `v1.1.0` |
| 5 | **输出** `output` | 产出了什么 | `186420 / 186420 条` |

> **顺序是固定的**：`input → time → interface → version → output`

#### 界面结构

```
┌─ 任务类别 [数据处理 ▾]  任务记录 [清洗任务（tsk_process_demo_01）▾] [查询] ─┐
│                                                                            │
│ ┌────────────────────────────────────────────────────────────────────────┐│
│ │ 证据字段                      [只读来源证据]                            ││
│ │ tsk_process_demo_01 / 未记录版本              ← 标题：谁 / 哪个版本      ││
│ │                                                                        ││
│ │ 对象内部编号   tsk_process_demo_01                                      ││
│ │ 证据编号       evidence-process-tsk_process_demo_01                     ││
│ │ 记录时间       2026/10/5 19:55:17                                       ││
│ │ 原始 Trace     trace_process_demo_01                                    ││
│ │ 版本引用       v1.1.0                                                   ││
│ │ 完整性         [已核验]                                                 ││
│ │                                                                        ││
│ │ 证据字段                                                                ││
│ │ 以下为该条证据记录里保存的原始字段值。五要素是否齐备属于整条链的结论，     ││
│ │ 请在「全链路追踪」查看。                                                ││
│ │ ┌────────┬──────────────────────────────┬──────────┐                  ││
│ │ │ 字段    │ 记录值                        │ 字段状态  │                  ││
│ │ ├────────┼──────────────────────────────┼──────────┤                  ││
│ │ │ 输入    │ v1.0.0                       │ [已核验]  │                  ││
│ │ │ 时间    │ 2026-10-05T19:55:17          │ [已核验]  │                  ││
│ │ │ 接口    │ 标准清洗流程 → normalize_text │ [已核验]  │                  ││
│ │ │ 版本    │ v1.1.0                       │ [已核验]  │                  ││
│ │ │ 输出    │ 186420 / 186420 条            │ [已核验]  │                  ││
│ │ └────────┴──────────────────────────────┴──────────┘                  ││
│ └────────────────────────────────────────────────────────────────────────┘│
└────────────────────────────────────────────────────────────────────────────┘
```

#### 关键设计

| 设计 | 说明 |
|---|---|
| **两级选择器** | 先选**任务类别**（数据处理 / 数据接入 / …），再选该类别下的**任务记录** |
| **任务名带 ID** | 因为很多任务重名，**带 ID 才能区分** |
| **「字段状态」而不是「核验」** | 这一列说的是**这一个字段**的状态，不是整条链的结论 —— **避免误导** |
| **提示语明确边界** | "五要素是否齐备属于整条链的结论" —— 按钮旁边就是这么写的 |

#### 数据来源

| 页面元素 | 接口 / 规则 |
|---|---|
| 任务类别下拉 | `capability_code` 经前端枚举表转中文（8 类） |
| 任务记录下拉 | `GET /tasks?page=1&pageSize=100`（分页拉全量） |
| 五要素证据 | `GET /compliance/evidence/{evidenceId}` |
| **evidenceId 怎么拼** | `data_process` → `evidence-process-{任务id}`；其他类型 → `evidence-task-{任务id}` |

> ⚠️ **当前只有「数据处理」类任务有证据数据**，其他 7 类点进去会看到：
> 「这个任务在后端还没有登记五要素证据，暂时无法筛查。」

```

#### 「检查点」是什么，为什么重要

| | 说明 |
|---|---|
| **是什么** | 训练过程中每隔几轮给模型存一次"存档"，万一练坏了能回退 |
| **存档规则** | **每 `⌊总轮数 ÷ 3⌋` 轮存一次，最后一轮必存**（例：10 轮 → 第 3、6、9、10 轮） |
| **为什么要查** | 出事时要能回答"当时的模型是什么样的"。**该存的没存 = 说不清** |

#### 关键设计

| 设计 | 说明 |
|---|---|
| **损失曲线 + 检查点标记** | 曲线上用**绿实心点**标已存的、**红空心圈**标该存没存的 —— 一图看完"训练正常吗 + 存档齐吗" |
| **横轴按「计划轮数」铺开** | 不是因为记录了 5 轮就只画 5 格 —— **右侧留白如实表示"这段没有训练日志"** |
| **损失值从逐轮日志取** | 所以**没存档的轮次也能看到当时的损失值** |
| **结论句** | 把"缺哪几轮"翻译成人话，不用自己数 |

#### 数据来源

| 页面元素 | 接口 |
|---|---|
| 训练任务下拉 | `GET /model-workbenches/current` → `training[]` |
| 逐轮损失 / 验证损失 | 同上 → `loss[]` / `validationLoss[]` |
| 检查点清单 | 同上 → `checkpoints[]` |
| 神经元激活 | `GET /compliance/contexts?source_kind=model` → `GET /compliance/audits/{id}`（`neuron_audit` 报告） |

> ⚠️ **神经元激活目前"只做了界面"**：
> 本地没有部署模型，读不到模型内部的激活数据。**示例演示模式下能看到完整效果**，真实接口模式下显示说明文字。

│ │任务层 │ 任务（tsk_xxx）   │ 执行失败：源数据…  │[待处理]│ 💬 0     │  │
│ │模型层 │ 训练任务 TR-…     │ 应有第 3 轮的检查点│[待处理]│ 💬 1     │  │
│ └──────┴──────────────────┴──────────────────┴──────┴──────────┘  │
└────────────────────────────────────────────────────────────────────┘
```

#### 关键设计

| 设计 | 说明 |
|---|---|
| **条数与总览页卡片一致** | 都是 10 —— **点进来不会对不上** |
| **每条有稳定编号** | 编号由业务对象拼成（如 `link:输入数据引用:edge-xxx`），**评论挂在这个编号上** |
| **「已修复」自动判定** | 上一轮出现过、本轮消失 → 标记已修复，**灰显保留**，评论不丢 |
| **每条能评论** | 讨论挂在具体问题上，不用另开文档 |
| **可追到源头** | 点「查看明细」跳到对应的细查页 |

#### 「已修复」是怎么判定的

```
第 1 次检查：算出 10 条问题  →  存档
第 2 次检查：算出 9 条问题   →  少了的那 1 条判定为「已修复」
                                仍然留在清单里（灰色），历史评论保留
```

**这个判定完全在前端浏览器里做**（存在本机），**后端不需要参与**。

## 六、演示模式 vs 真实接口

**页面右上角有一个开关**（`真实接口` / `示例演示`）：

| 模式 | 数据来自 | 用途 |
|---|---|---|
| **真实接口** | 后端数据库 | 真实审计 |
| **示例演示** | 前端内置演示数据 | **演示 / 汇报 / 没有后端时也能跑** |

> **⚠️ 演示模式下有个例外**：模型内部审计的「神经元激活」只有演示模式能用
> —— 因为本地没有部署模型，采集不到真实的神经元激活。

## 八、一句话总结

> **「全链路合规治理」= 三层检查（链路 / 任务 / 模型）
> + 三个细查页（谱系 / 五要素 / 模型内部）
> + 一张统一问题清单（可评论、可标记已修复）
> 所有结论都追得到源证据，所有"查不了"的情况都如实说明原因。**
